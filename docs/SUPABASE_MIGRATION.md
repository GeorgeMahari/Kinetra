# Moving the Kinetra database to Supabase

Target: Supabase PostgreSQL 17.12, reached through the Session Pooler (IPv4, port 5432, TLS). FastAPI
stays the only client: it keeps its own JWT authentication, its SQLAlchemy models and its Alembic
migrations. The local Docker database (`kinetra-db-1`, PostgreSQL 18.1) is only read, never changed,
and stays as the fallback.

## 1. Findings (2026-11-17)

| Item | Local | Note for Supabase |
|---|---|---|
| Server | PostgreSQL 18.1 | Supabase 17.12: a downgrade, so the schema is **not** restored from a PG18 dump |
| Schema | 19 tables (incl. `alembic_version`), 2 enums (`user_status`, `sex_for_norms`), 80 constraints (19 PK, 19 FK, 6 unique, 36 check), 36 indexes | All created by Alembic 0001–0010. No functions, triggers, views, sequences or identity columns. The UUIDs are generated by the app |
| Extensions | `plpgsql` only | Nothing to enable |
| PG18-only features | none used (no virtual generated columns, no `NOT ENFORCED`, no `uuidv7()`) | PG18 also records NOT NULL as catalog constraints, which matters only to a schema dump |
| Seed data | `sports` (33 rows) inserted by migrations 0003 and 0010 | Created by Alembic on the target; compared, not copied |
| Data | users 2, test_results 235, refresh_tokens 117, measurements 63, … (17 data tables) | Copied as is: same UUIDs, timestamps and relations |
| Connection | `KINETRA_DB_*`, password from `POSTGRES_PASSWORD` | `KINETRA_DB_SSLMODE`, `KINETRA_DB_SSLROOTCERT`, pool size and timeout are now settings, and `KINETRA_DB_PASSWORD` wins over `POSTGRES_PASSWORD` |
| Driver | psycopg 3 (prepares a statement after 5 runs) | Session mode supports prepared statements; transaction mode (6543) would not |
| Access model | API-only, per-user filtering in the services, covered by the isolation tests | Supabase's Data API is not used. It must not reach these tables (see §3) |

## 2. Strategy and why

1. **Schema from Alembic, not from a dump.** `alembic upgrade head` builds the schema on 17.12
   exactly as on 18.1, keeps `alembic_version` correct for future migrations, and avoids
   PG18-specific dump syntax.
2. **Data from a data-only dump, in one transaction.** `infra/supabase/transfer-data.ps1` runs
   `pg_dump --data-only` and pipes it into `psql -1 -v ON_ERROR_STOP=1`, both inside the local
   container, so no file with personal data is written on the host. All constraints stay active:
   either every row goes in, or nothing does. The script:
   - refuses to start when the target is not at the same Alembic revision;
   - refuses to start when any target data table already holds rows (it never overwrites);
   - compares a row count and an md5 checksum of every table on both sides.
3. **Least privilege.** Migrations run as `postgres`, which owns the tables. The API logs in as
   `kinetra_app`: select / insert / update / delete only, no DDL, no TRUNCATE, no RLS bypass,
   `statement_timeout` of 30 s and a connection limit of 20. Only a SCRAM verifier of its password
   is sent.

## 3. Security on Supabase

- New tables in `public` on existing projects get privileges for `anon` and `authenticated` by
  default, which makes them reachable through the Data API with the public key.
  `db/sql/supabase/02_security.sql` revokes these privileges and the default privileges for future
  tables.
- RLS is enabled on every table. The only policy admits `kinetra_app`. Even a privilege granted
  by mistake later shows no rows through the Data API (checked in the rehearsal).
- Per-user isolation stays in the API (`user_id` taken from the token). Policies of the form
  `auth.uid() = user_id` do not apply here, because the people are not Supabase Auth users.
- Recommended in the dashboard: turn **Data API off** (Integrations → Data API), since nothing
  uses it, and turn **Enforce SSL** on. Then connect with `sslmode=verify-full` and the project's
  CA certificate (`KINETRA_DB_SSLROOTCERT`).
- No secret is in a file. The secrets live in user environment variables:
  - `SUPABASE_DB_PASSWORD` (postgres, admin; used for migrations and security only);
  - `KINETRA_APP_DB_PASSWORD` (the API).

  The scripts pass them to processes through the environment, never on a command line.

## 5. Procedure on Supabase (each step needs the owner's approval)

| # | Step | Writes to Supabase |
|---|---|---|
| 0 | Fresh local backup (`infra/public/backup-db.ps1`), next to `kinetra_pre_supabase.dump`. Stop the local API, so no new data arrives during the copy | no |
| 1 | Pre-flight, read-only: server version, existing tables in `public`, roles, connection over TLS | no |
| 2 | `alembic upgrade head` as `postgres.<ref>` | yes: creates the 19 tables and the `sports` rows |
| 3 | `apply-security.ps1`: role `kinetra_app`, privileges, RLS | yes |
| 4 | `transfer-data.ps1` | yes: inserts the data in one transaction, then verifies |
| 5 | Run the API against Supabase as `kinetra_app`, then `smoke_test.py` | yes: creates and deletes two test accounts |
| 6 | Switch `infra/public/start-public.ps1` to Supabase | no |

Rollback: until step 6 the app still uses the local database, so nothing changes for users. If a
step fails, the Supabase tables can be removed with `alembic downgrade base`. That command is
destructive, so it runs only with explicit approval.

## 6. Backups and restore

- **Local (unchanged):** `infra/public/backup-db.ps1` writes `db/backups/kinetra_<date>.dump`.
- **Supabase:** dump with a PostgreSQL 17 client, so the file restores on 17:
  ```powershell
  $env:PGPASSWORD = [Environment]::GetEnvironmentVariable('SUPABASE_DB_PASSWORD','User')
  docker run --rm -e PGPASSWORD -v "${PWD}\db\backups:/backups" postgres:17-alpine `
    pg_dump "host=<pooler-host> port=5432 dbname=postgres user=postgres.<ref> sslmode=require" `
    --schema=public --format=custom --no-owner --no-privileges --file=/backups/supabase_<date>.dump
  Remove-Item Env:PGPASSWORD
  ```
  The dashboard also lists the platform backups that the project's plan includes.
- **Restore into an empty Supabase project:**
  1. Run `alembic upgrade head`.
  2. Run `apply-security.ps1`.
  3. Run `pg_restore --data-only --single-transaction --exclude-table-data=sports --exclude-table-data=alembic_version`
     with the same client container.

  Restoring over existing data replaces it, so it needs a fresh backup and an explicit decision.
- **Back to local:** the local database is untouched. Point `KINETRA_DB_*` back to the defaults, or
  remove the variables.
